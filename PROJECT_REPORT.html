01

What it is

The application is organised as three layers, and that split explains almost every design decision in the code:

  • Layer 1 — real OS monitors. File system, processes, network, USB devices and the Windows Event Log. These start automatically on launch and are the primary data source.
  • Layer 2 — demo data generator. Opt-in, clearly labelled, produces synthetic employee activity so the dashboard has something to show on a quiet machine.
  • Layer 3 — analysis and response. The risk engine, the anomaly model, the sentiment analyser, alerts, incidents and reports. It consumes whatever rows appear in activity_logs and does not care which layer wrote them.

The seam between the layers is a single table. Layers 1 and 2 both write the same row shape, which is why the analysis layer can be swapped, retrained or replaced without touching the collectors — and it is where a different model plugs in later.

Stack: Python, CustomTkinter for the desktop UI, matplotlib for charts, SQLite for storage, scikit-learn for the anomaly model, NLTK VADER for sentiment, ReportLab for PDF export, psutil, watchdog and pywin32 for the monitors. No network calls; nothing leaves the machine.

02

How it starts

main.py is 57 lines and does four things, in this order:

db.init_db(seed=True)              # 1. create tables, seed settings + 10 employees
try:
    anomaly_detector.ensure_trained()  # 2. train the model if no bundle exists
except Exception as exc: ...
app = Application()                # 3. build the window
app.mainloop()                     # 4. hand control to Tk

Inside Application.__init__ the order matters. It builds the risk engine (reading saved weights and threshold out of the settings table), then the MonitorManager, then the demo generator, then the ten pages, and only then calls monitors.start_all() and raises the Dashboard. Each monitor gets its own daemon thread.

Threading rules

Every monitor runs on a background thread and calls back into the app when it observes something. Tkinter is not thread-safe, so the callbacks do not touch widgets directly. They marshal through the event loop:

def _on_monitor_event(self, event):
    self.after(0, lambda: self._dispatch_monitor_event(event))   # onto the main loop

_dispatch_monitor_event then fans the event out to four pages — Dashboard, Live Monitoring, AI Risk Prediction and Security Alerts — each of which implements an optional on_monitor_event hook. The demo generator has a parallel path through on_demo_event.

The important asymmetry: the monitor path also triggers risk_engine.assess_all() inside MonitorManager. The demo path does not. So in demo-only mode the feed fills up but risk scores never move.

Launch blocker main.py imports gui.app, which imports gui.live_monitoring. That module has an f-string syntax error on line 167 (nested same-type quotes) that is legal only from Python 3.12 onward. On Python 3.11 the app cannot start at all.

04

Risk engine

The engine is rule-based and time-windowed, in engine/risk_engine.py. Each event type carries a weight; only events inside a rolling 60-minute window count; older events are decayed so risk bleeds off instead of staying elevated forever.

Weights

privilege_escalation18
usb_copy15
bulk_data_transfer15
restricted_file_access12
large_download10
failed_login8
unusual_login_time5
normal_activity0

Formula

for each event inside the 60-minute window:
    decay  = max(0.4, 1 − age_minutes / 60)
    contribution[type] += weight[type] × decay

score = min(100, Σ contribution[type]
                 + 1.0 × Σ max(0, count[type] − 3))

The min(100, …) cap is RISK_SCORE_CAP. The second term is a flood bonus: past three occurrences of any one event type, each extra one adds a flat point, so a burst of low-weight noise can accumulate on its own. The decay floor of 0.4 means an event never decays below 40% of its weight while still inside the window.

Worked example

3 × usb_copy          age 10 min   decay 0.833   15 × 0.833 × 3 = 37.5
1 × privilege_escalation  age 5 min  decay 0.917   18 × 0.917     = 16.5
flood bonus   max(0, 3−3) + max(0, 1−3) = 0
                                        ─────────────
score 54.0  →  HIGH  (50–74)  →  threshold 20 crossed  →  alert + incident

Bands and threshold

BandFromToMeaning in the UI
LOW019green — normal
MEDIUM2049amber; this is the alert threshold
HIGH5074red

Weights and threshold are editable from the Settings page and persisted as JSON in the settings table, so a restart picks up whatever the operator last saved.

What a pass writes

assess_all() loops every user and, per user, calls update_user_risk, then insert_risk_history, then — if the score is at or above the threshold — _maybe_create_alert. That last step reuses any open incident for the same user instead of opening a duplicate, then inserts an alert, links it to the incident, and writes an audit row.

Analysis blocker Line 182 asks the database module for severity_from_score, which lives in utils/helpers.py and was never re-exported. Any threshold breach therefore raises AttributeError mid-loop. Two consequences: no alert or incident is ever created, and the loop aborts, so users ordered after the triggering one are not scored that pass.
05

Anomaly model

Alongside the rules sits an unsupervised IsolationForest in ai/model_training.py. It answers a different question: not "did a weighted event fire" but "does this user's aggregate behaviour look unlike everyone else's".

Features — one row per user, last 60 minutes

FeatureHow it is aggregated
login_hourhour of the newest event in the window that carries one
failed_login_countcount of failed_login events
files_accessedsum of files_accessed
download_volume_mbsum of download_mb
usb_activitycount of rows where usb_activity > 0
privileged_access_countcount of rows where privileged > 0
data_transfer_mbsum of data_transfer_mb

Everything is aggregated from activity_logs, which is why the same seven columns exist on the event row in the first place. A user with no events in the window becomes an all-zero feature row, not a missing one.

Training

Training data is 800 synthetic "normal employee" rows drawn from fixed distributions (seed=42: login hour normal around 09:00, Poisson failed logins, clipped normals for volumes) concatenated with the real per-user rows. A StandardScaler is fitted, then the forest. The result is persisted as a joblib bundle with four keys — model, scaler, metadata, feature_columns — to models/isolation_forest.joblib.

The bundle on disk

FieldValue

Worth reading closely real_samples is 10 — one aggregate row per seeded employee. So the model is effectively trained on synthetic data, with the machine's own activity contributing ten summary rows. That is a deliberate cold-start choice, not an accident, but it means anomaly scores are "unlike the synthetic baseline", not "unlike this organisation".

Inference contract

predict_anomalies(user_ids=None) returns one dict per user:

{
  "user_id":       42,
  "user_name":     "Dana Whitfield",
  "anomaly_score": -0.0812,          # decision_function; lower = more anomalous
  "is_anomaly":    True,             # from predict(): -1 anomaly, 1 normal
  "label":         "ANOMALY",
  "top_factors":   [ {feature, value, weight, label}, ×3 ],
  "features":      { 7 raw aggregated values }
}

This dict is the entire interface between the model and the rest of the application. Four call sites consume it: the Dashboard's "AI Anomalies" KPI tile, the AI Risk Prediction page, the Settings page's model panel, and the startup pre-train.

How "top factors" is computed

_top_contributors averages each tree's feature_importances_, then ranks features by |scaled value| × importance and keeps three. The measured mean importances sum to 1.0 and are led by login_hour (0.219), download_volume_mb (0.213), files_accessed (0.205) and data_transfer_mb (0.199); usb_activity (0.041) and privileged_access_count (0.038) trail.

Treat that ranking as a heuristic. The base estimators use splitter="random", so which feature a split lands on is partly a random choice, and the purity-based importance therefore reflects that rather than how predictive a feature is for this data. The deviation term (|scaled value|) does most of the real work — the importances act as a mild re-weighting on top of it.

Missing validation predict_anomalies never checks that a requested user exists. Ask for user 99999 and you get a confident-looking NORMAL verdict for "User 99999", built from an all-zero feature row. This is the cause of the one failing test in the suite.

Event handling

MonitorManager._handle_event resolves a user (currently always the first row in users, documented in the code as a demo limitation), inserts the activity row, then calls risk_engine.assess_all(). That last call is wrapped in a log.debug — which is why the alert crash above is invisible at runtime.

Data model

One SQLite file, insider_threat.db, in the project root. schema.sql is applied on every startup with CREATE TABLE IF NOT EXISTS, so it is idempotent. PRAGMA foreign_keys = ON is set on each connection and children cascade from users.

TableHoldsKey columns
usersthe monitored populationname, department, role, risk_score, account_status, 3 baseline_*
activity_logsevery observation, and the ML feature inputsevent_type, risk_points, login_hour, files_accessed, download_mb, usb_activity, privileged, data_transfer_mb
risk_historyone row per user per assessmentrisk_score, explanation
alertsthreshold breachesseverity, status, incident_id
incidentscase records, auto-opened by the enginetrigger_score, status, summary
response_actionsthe response audit trailaction_type, performed_by
sentiment_historyVADER results over timecompound, positive, neutral, negative, label
challenge_scorestraining-game resultsparticipant, challenge, score, correct, total

Three indexes: (user_id, timestamp) on activity_logs, and status on both alerts and incidents.

Access pattern

db_manager opens a fresh connection per operation via _connect(), with a get_conn() context manager handling commit and rollback. Rows come back as sqlite3.Row. Simple, and safe against cross-thread reuse — but every monitor event pays a connection open, and assess_all opens one per user per pass.

Baselines

users carries baseline_login_hour, baseline_daily_downloads and baseline_file_access. They are editable on the User Management page and exported in reports, and the demo generator reads baseline_login_hour to decide what counts as an unusual login time. Neither the risk engine nor the anomaly model uses them: the engine scores against fixed global weights, and the model compares raw aggregates without any per-user normalisation. That is the single biggest conceptual gap between what the schema is shaped for and what the analysis actually does.

Charts are matplotlib figures embedded with FigureCanvasTkAgg and styled by style_dark_axes. Tables are ttk.Treeview restyled through style_treeview, because CustomTkinter does not theme ttk widgets. gui/theme.py is the shared layer: cards, KPI tiles, buttons, entries, section headers and the severity colour map all live there, and the page modules do not repeat any of it.

The Dashboard refreshes on a 4-second after loop, with change-detection guards on each chart so an unchanged value does not trigger a redraw. Model inference is the expensive part, so the "AI Anomalies" tile is recomputed at most every 30 seconds regardless of the refresh rate.

09

Subsystems

Sentiment

ai/sentiment_analyzer.py scores text with NLTK VADER and falls back to a small built-in lexicon when the VADER corpus is missing. Results persist to sentiment_history. Exposed as a module-level singleton via get_analyzer().

Incident response

response/incident_response.py defines five actions — acknowledge, investigate, contain, restore, resolve — with recommended_actions keyed by incident status. Actions mutate application state only. Nothing touches a real account, which is the safety property the README claims and the code honours.

Gamification

gamification/challenges.py holds the question bank and scoring; the Cyber Challenges page renders it and maintains the leaderboard from challenge_scores.

Reporting

CSV export writes the raw tables; the PDF path uses ReportLab. Both land in reports/.

Demo generator

engine/event_simulator.py emits weighted random events on a timer, choosing each event's user and — for unusual-login events — an hour at least four away from that user's baseline.

Helpers

utils/helpers.py owns the cross-cutting utilities: timestamp formatting, clamping, logging setup, band_for_score and severity_from_score.

Verified findings

Everything below was confirmed by running the code, not by reading it alone. Two are blockers; the rest are ordered by how much they distort what the system appears to do.

gui/live_monitoring.py:167Launch blocker: f-string syntax errorblocker

A nested f-string reuses single quotes inside a single-quoted f-string. Legal only from Python 3.12; py -3.11 -m compileall gui fails. Since main.py → gui.app → this module, the app cannot start on 3.11 — the version the README targets.

engine/risk_engine.py:182Launch blocker: alerts never fireblocker

db.severity_from_score does not exist on the database module; the function is in utils/helpers.py. Reproduced with a score of 57.99 against a threshold of 20: AttributeError, alerts created 0, incidents 0. The exception also aborts assess_all's loop, so later users go unscored. Corroborated in the live database: 279 activity rows, zero alerts, zero incidents, zero audit rows.

gui/app.py:285Demo mode never scores anythinghigh

_dispatch_demo_event notifies pages but never calls assess_all, unlike the monitor path. In demo-only mode risk scores never change and no alert can ever fire, which contradicts the README walkthrough.

utils/helpers.py:63Self-assignment in the default-band pathhigh

Inside the bands is None branch, bands = bands should assign RISK_BANDS. Latent today because every caller passes bands explicitly; the first caller that relies on the default gets None.items().

ai/model_training.py:186Unknown user ids produce a verdictmedium

No validation of requested ids, so an unknown id yields a fabricated all-zero feature row and a confident NORMAL label. This is the single failing test, test_predict_for_unknown_user.

gamification/challenges.py:106
gui/gamification.py:205Every challenge answer is counted twicemedium

evaluate_answer inserts a score row under a hardcoded demo_user, and the page inserts a second one. The leaderboard double-counts.

gui/gamification.py:163Quiz options are not mutually exclusivemedium

Each radio button gets its own StringVar, so multiple options can appear selected at once. _submit quietly grades the lowest-index selection.

monitor/monitor_manager.py:123O(events × users) rescanmedium

assess_all() runs on every event. Measured ~3 events/sec while idle, and each pass rescans all activity for all ten users on a fresh connection, per event.

monitor/eventlog_monitor.py:82Event log re-emits the newest recordsmedium

The read uses offset 0 with no record bookmark, so each 5-second poll re-delivers the most recent events and inflates the feed and the scores.

engine/risk_engine.py:170risk_history grows without boundmedium

One row per user per assessment, while the reader latest_risk_history is called from nowhere. Live database: 674 history rows against 279 activity rows, and climbing with every event.

monitor/usb_monitor.py:65Fixed drives read as USB copieslow

The is_removable check accepts a bare filesystem type (ntfs, vfat…) as sufficient, so internal volumes can score 15 points as removable-media use.

monitor/process_monitor.pyRoutine service starts score as escalationlow

Any SYSTEM account or any system32 executable counts as privilege_escalation — 18 points for ordinary Windows activity.

database/db_manager.py:27Discarded connection and dead keylow

An import-time sqlite3.connect whose result is thrown away, plus a random import with no consumer, and the sim_interval_ms / demo_interval_ms key mismatch described in section 10.

README.mdDocs drift from the codelow

Monitor names in the README do not match the keys the code uses, and the walkthrough skips steps 5, 8 and 10. _top_contributors' docstring says top-2; the code takes three.

Where to start The two blockers are one-line fixes in different files, and fixing the second one is what actually turns the alert pipeline on for the first time. Everything else is quality, not correctness of the pipeline itself.
12

Plugging in a model

Not started — this section records the seam, for when the trained model is ready.

The clean insertion point is ai/anomaly_detector.py. It is already a thin facade over model_training, exposing is_trained, is_available, unavailable_reason, ensure_trained, train, predict_for_all, predict_for_user, model_info and summary. Nothing else in the application imports model_training directly, so swapping what sits behind that facade changes no page code.

Its consumers, all of which only read predict_anomalies output and the summary:

  • main.py — startup pre-train
  • gui/dashboard.py — the "AI Anomalies" KPI tile, throttled to 30 s
  • gui/ai_predictions.py — the main table, factor breakdown, retrain button
  • gui/settings_page.py — model status panel and retrain

Two shapes of change

If the trained artefact is a scikit-learn estimator, the change is small: produce a joblib bundle with the same four keys — model, scaler, metadata, feature_columns — drop it at models/isolation_forest.joblib, and the existing loader picks it up unchanged, provided it consumes the same seven columns in the same order. Features that need different inputs mean editing build_user_features and FEATURE_COLUMNS together, because the stored feature_columns list is what the scaler is applied against.

A transformer or LLM checkpoint is a different proposition. It pulls transformers, torch and huggingface_hub into requirements.txt, needs weights present locally to keep the no-network promise, and needs a decision about whether it replaces the IsolationForest or runs beside it — the facade supports either, but the "top factors" explainability the AI page renders is specific to the tree-based path.

Two questions will settle which of these it is: what the model was trained to predict, and whether it consumes the seven existing features or its own input.
